# L2 асистент — підсумок роботи

Документ фіксує, що робили з проєктом, які спроби вводу перевіряли і до яких висновків дійшли.

**Репозиторій:** https://github.com/bigGlebowski92/l2_assistent  
**Середовище:** Windows 10/11, Python 3.12, клієнт Lineage 2 (Scryde / інші приватні сервери).

---

## 1. Старт проєкту

1. Клоновано репозиторій `l2_assistent` у робочу папку.
2. У репо не було `run.bat` — запуск за README: `python ui.py`.
3. Встановлено Python 3.12 (winget) і залежності з `requirements.txt`.
4. Додано `run.bat` для зручного запуску.
5. З’ясовано: гру часто запущено **від адміністратора** → асистент теж треба запускати elevated (UAC), інакше Windows (UIPI) блокує ввід у вікно гри.

---

## 2. Що вміє асистент (поточна логіка)

- Зчитує **HP цілі** і **моє HP** з екрана (mss + детекція червоних стовпчиків смуги).
- За HP вирішує: наводити курсор на слот **F1** (атака) або **F2** (наступна ціль).
- **Клік не робить** — клік очікується від макросу на миші.
- **F12** — глобальний стоп (бібліотека `keyboard`).
- Калібрування: рамки HP + точки наведення F1/F2.
- Налаштування в `config.json`.

---

## 3. Проблеми з читанням HP

| Симптом | Причина | Що зробили |
|--------|---------|------------|
| HP цілі завжди 0% | Рамка калібрування захоплювала ім’я + смугу; скан був лише по **середині** кадру | Скан усієї висоти області |
| Після зміни сервера/UI знову 0% | Темніший червоний / інша геометрія UI | Ті самі пороги + повний скан; калібрувати ближче до червоної смуги |
| BitBlt / mss | Тимчасові збої захоплення екрана | Повтори grab + fallback |

Тести: `test_hp.py` (синтетичні BGRA).

## 4. Спроби програмного вводу — клавіатура

Мета: натискати F1/F2 з Python.

### Бібліотеки

| Метод | Результат |
|-------|-----------|
| `keyboard` (press/send) | API OK, гра не реагує |
| `pydirectinput` (DirectInput scan codes / SendInput) | API OK, гра не реагує |
| `pyautogui.press` | API OK, гра не реагує |
| `pynput` (`Key.f1`) | API OK, гра не реагує |
| `win32api.keybd_event` / `ctypes keybd_event` | API OK, гра не реагує |

### Низькорівневі Windows API

| Метод | Результат |
|-------|-----------|
| `SendInput` (scancode) | Подія вставлена, гра не реагує |
| `PostMessage(WM_KEYDOWN/UP)` у HWND viewport | Повертає успіх, гра не реагує |
| `SendMessage(WM_KEYDOWN/UP)` | Виклик проходить, ефекту в грі немає |

### Додаткові спостереження

- Без прав адміністратора (гра elevated, асистент — ні) ввід блокується UIPI.
- Навіть з admin + фокусом на грі **софт-клавіші** клієнт відкидає.
- Тест усіх методів підряд: `key_methods_test.py` (лог у TEMP / `key_methods_result.txt`). Усі виклики без exception; у грі F1 не спрацьовував.

**Висновок:** клієнт фільтрує injected keyboard (DirectInput / anti-cheat). Зміна бібліотеки Python майже нічого не дає.

## 5. Спроби програмного вводу — миша

| Підхід | Результат |
|--------|-----------|
| `SetCursorPos` + `mouse_event` (ЛКМ) | Інколи **перший** клік проходить, далі — ні (курсор їде, кліка немає) |
| `SendInput` absolute mouse | Те саме / нестабільно |
| Подвійний тап, довше утримання, settle delay | Не стабілізувало |
| Відвести курсор і повернути («свіжий» клік) | Не стабілізувало |
| `PostMessage(WM_LBUTTONDOWN/UP)` у HWND гри | Не дало стабільного кліка |
| Наведення + софт-клік у циклі | Конфлікт із таймінгом; кліки «губляться» |

**Висновок:** софт-клік миші частково проходить (рідко / перший раз), повторний injected клік клієнт часто ігнорує.

---

## 6. Еволюція режиму роботи асистента

1. **Клавіші F1/F2** — основний задум README.  
2. Фокус вікна гри (`SetForegroundWindow`, Alt-trick) — прибрано: користувач сам перемикається на клієнт.  
3. **Лише кліки** по слотах панелі.  
4. Кліки + клавіші одночасно.  
5. Знову лише клавіші / знову лише кліки — залежно від сервера.  
6. **Поточний режим:** лише **наведення** курсора на F1/F2; клік — макросом на миші; F12 — стоп.  
   Курсор рухається **тільки при зміні слота** (F1↔F2), щоб не збивати макрос.

---

## 7. Макрос на миші (залізо / софт виробника)

Очікування: макрос ЛКМ кожні ~500 мс + асистент лише наводить.

Факти від користувача:

- Макрос ЛКМ **не працює** навіть **без** асистента.
- Поки макрос активний, не відкривається навіть трей Windows.
- Після **фізичного** натискання ЛКМ щось «оживає».
- Те саме через **Lua** у ПЗ миші.

**Висновок:** макрос/Lua в G Hub / Synapse тощо часто шле **той самий software click**, а не HID з прошивки. Потрібен справжній **on-board** макрос у пам’яті миші (якщо модель підтримує) або інша миша з нормальною прошивкою макросів.

---

## 8. Чому гра відрізняє «справжній» і «програмний» ввід

1. Фізична клавіатура/миша → драйвер HID → система.  
2. Python / AutoHotkey / Lua миші → `SendInput` / `mouse_event` / PostMessage → подія з міткою **injected**.  
3. Клієнт (DirectInput / raw input / захист) може ігнорувати injected.  
4. Макрос у чипі миші виглядає як звичайний HID — якщо він справді в прошивці.

## 10. Підсумкові висновки

1. **Читання HP з екрана** — працює після правильного калібрування і скану всієї області.  
2. **Програмні клавіші** (усі перевірені бібліотеки й WinAPI) — для цього клієнта **не працюють**.  
3. **Програмні кліки** — нестабільні (часто лише перший).  
4. **Макрос/Lua миші** у софті виробника — часто теж software; без on-board ефект той самий.  
5. Практична схема: асистент **наводить** на F1/F2 → клік дає **апаратний** макрос (якщо вдасться налаштувати) або ручний клік.  
6. Асистент і гру краще запускати з **однаковими** правами (обидва admin або обидва звичайні).

## 11. Хронологія ключових змін у коді (стисло)

1. Клон + запуск + залежності.  
2. Admin / `run.bat`.  
3. Пошук/фокус вікна гри → спрощення → прибрано.  
4. Виправлення HP-скану (уся висота).  
5. Цикли: keys ↔ clicks ↔ hybrid.  
6. Стабілізація кліків (SendInput, repeat, PostMessage) — без стабільного успіху.  
7. Режим **aim-only** + F12.  
8. Наведення лише при зміні слота (під макрос миші).  
9. Порівняльний тест усіх методів клавіатури — жоден не спрацював у грі.
